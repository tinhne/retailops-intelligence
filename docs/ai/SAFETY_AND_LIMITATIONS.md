# AI Safety and Limitations

> **Status:** Design (v1), task T-070. Applies to the copilot, investigation summaries, and note
> drafting. Related: [AI_ARCHITECTURE.md](AI_ARCHITECTURE.md), [TOOL_CATALOG.md](TOOL_CATALOG.md),
> [PROMPT_DESIGN.md](PROMPT_DESIGN.md), `SECURITY.md` (T-082).

## 1. Position

The copilot is an explanation layer over a deterministic system. The rule engine decides what is an
exception, how severe it is, and how it ranks. The copilot reads the same data through the same
permissions as the user, and a person makes every change. The safety design follows from that: the
copilot is given no way to change data, see more than the user can see, or reach anything outside
the store, so that a wrong or manipulated answer stays a wrong answer and never becomes a wrong
action.

The live LLM path uses **free-tier APIs only** (owner decision, 2026-10-31): Google Gemini by
default, or an OpenAI-compatible endpoint with a free tier. Without a key, or whenever the live
provider is unavailable, the rule-based (deterministic) assistant answers from the same data.

## 2. Guardrails

| Guardrail | Implementation | Verified by |
|---|---|---|
| Tool allowlist | Exactly 11 read-only tools (`TOOL_CATALOG.md`). No raw SQL, write, external, cross-store, user-lookup, audit, or settings tools | Registry unit test: the registered set equals the catalog |
| Permission checks | `copilot.use` on every copilot endpoint, the feature permission (`exceptions.read` for summaries, `exceptions.work` for note drafts), and each tool's own read permission through `require_permission` | Per-tool permission tests (T-071), API permission matrix (`TEST_STRATEGY.md §7`), evaluation permission cases |
| Store scoping | `store_id` comes from the authorized request path, never from model output. Repositories filter by it (BR-003). Other-store ids return `NOT_FOUND`, identical to missing ids | Per-tool cross-store tests, tenancy evaluation cases |
| Size caps | ≤ 50 rows per tool (20 by default), ≤ 16 KB per result, ≤ 12 tool calls and ≤ 6 tool rounds per turn, input and output token caps, a 45 s turn deadline | Registry and loop unit tests |
| No writes | Tools run in `READ ONLY` transactions with a statement timeout. The `ai` module writes only its own tables. No tool maps to a mutating service function | Test that each tool's transaction is read-only; `no_mutation` evaluation assertions |
| Human confirmation | Recommendations are text. Acting on one means using the normal UI action, with its permission check, CSRF token, and audit entry under the person's name. A drafted note is saved only when a person accepts it (`ExceptionNote.source = AI_DRAFT_ACCEPTED`) | E2E journey step 8 (`TEST_STRATEGY.md §9`); API test that the draft endpoint writes no note |
| Grounding and validation | Every fact and metric must cite a record read in the same turn. Unverifiable references, unverified metrics, and unsupported estimates are dropped and flagged. Action claims and "loss" wording for exposure (BR-404) are rejected (`AI_ARCHITECTURE.md §6`) | Validator unit tests; attribution and unsupported-claim metrics |
| Provenance labels | See §3 | Component tests of the answer renderer |
| Injection defences | Untrusted-field marking, sanitisation, delimiters, plain-text rendering, no outbound tools (`PROMPT_DESIGN.md §5`) | Injection evaluation cases with canary tokens |
| Rate limits and budgets | 20 copilot requests per user per minute; a per-instance budget of live LLM requests and tokens (§6) | Rate-limit and budget unit tests |
| Secrets | `GEMINI_API_KEY` and `LLM_API_KEY` stay on the server: never sent to the browser, logged, or included in errors. `.env` is never committed | Settings test; log-redaction test |

## 4. Data sent to the LLM provider

Only the live adapters send data, and only to the one configured provider. The deterministic
provider makes no network calls.

| Sent | Not sent |
|---|---|
| The static system prompt and tool definitions | Passwords, password hashes, session tokens, CSRF tokens, API keys |
| The user's question and up to 4 prior questions and answer summaries of the same conversation | User email addresses, IP addresses, user agents |
| The store's name, currency, time zone, the turn's `as_of`, the user's role | Audit log entries |
| Tool results: business records of the one store (product SKUs and names, categories, prices, reorder settings, supplier names and lead times; order numbers, statuses, timestamps, totals, lines; inventory quantities and movements; exception evidence, priority, history; import summaries and issue rows) | Customer personal data. None exists: the product stores no customer names, emails, addresses, or phone numbers (BR-505) |
| Staff display names where they appear in exception assignments, events, and note authors | `customer_ref`, tracking numbers, unit costs, supplier contact references (excluded from tool output, `TOOL_CATALOG.md §1`) |
| Note bodies and import raw values (free text, truncated) | Records of any other store or organization |

**Free-tier data terms (limitation, Needs validation).** Free tiers of LLM APIs may allow the
provider to use submitted content to improve its products, and may differ from paid tiers in
retention and review. This project does not assert what any provider's current terms say. Before
the live provider is enabled for a deployment, the owner verifies the chosen provider's current
terms for the free tier and records the result in `docs/operations/DEPLOYMENT.md`. Consequences
that hold regardless of the outcome:

- The public demo sends only fictional demo data, so free-tier terms are acceptable there by
  construction (**MVP assumption**, to confirm with the terms check).
- No customer personal data can be sent, because none is stored (BR-505).
- What can be sent is the store's business records, staff display names, and free text that staff
  typed into notes. For a real store's data, a team should either accept the provider's free-tier
  terms knowingly, switch to a tier whose terms fit, or run with `LLM_PROVIDER=deterministic`.
- The copilot panel tells users not to paste personal data into questions or notes. Free text typed
  by users cannot be filtered reliably and is sent as typed when it is part of the turn.

## 5. Provider outage and quota behavior

| Situation | Behavior |
|---|---|
| Provider returns 429 or a quota-exhausted error (per minute or per day) | No retry. That answer comes from the deterministic provider with the fallback notice. The circuit opens for the provider's `Retry-After`, otherwise 60 s, doubling on consecutive quota errors up to 1 h |
| Timeout (20 s per request, 45 s per turn) | Deterministic answer with the notice |
| 5xx, connection failure, outage | At most one retry if the deadline allows, then the deterministic answer with the notice. Five failures within 60 s open the circuit for 60 s |
| This instance's own budget is spent (requests per minute, requests per day, tokens per day) | Deterministic answers with the notice until the window resets. The provider is not called |
| No key, or `LLM_PROVIDER=deterministic` | Deterministic answers with the "Rule-based assistant" label and no outage notice |

The user always gets an answer grounded in the same tools, with a label that says which assistant
produced it. The product's operational features (dashboard, exceptions, imports, inventory) do not
depend on the LLM at all.

## 6. Abuse controls and rate limits

| Control | Value | Notes |
|---|---|---|
| Copilot requests per user | 20 per minute (`COPILOT_RATE_LIMIT_PER_MINUTE`) | HTTP 429 with the standard error envelope. Applies to chat, summaries, regenerate, and drafts |
| Live LLM requests per API instance | 10 per minute and 500 per day by default (`LLM_BUDGET_REQUESTS_PER_MINUTE`, `LLM_BUDGET_REQUESTS_PER_DAY`) | Project caps set **below** the provider's free-tier limits. The defaults are placeholders: they must be set from the provider's current published limits for the chosen model (**Needs validation**) |
| Live LLM tokens per API instance | 1,000,000 per day (`LLM_BUDGET_TOKENS_PER_DAY`) | Same |
| Question length | 1–2,000 characters | 422 otherwise |
| Conversation length | 50 messages | The UI asks the user to start a new conversation |
| Note-draft hint | ≤ 500 characters | |
| Fixed answers | Help, refusals, and write requests are answered without an LLM request | Removes cheap ways to burn quota |
| Summary cache | Repeat views of an unchanged exception cost no LLM request | `AI_ARCHITECTURE.md §8.3` |
| Login | 5 per minute per IP and email | From the platform rate limits |

**Limitation: in-process counters.** The HTTP rate limiter and the LLM budget are in memory and per
API instance. Restarting an instance resets them, and several instances would each spend their own
budget against one shared provider quota. Scaling out needs a shared store (for example Redis),
which v1 deliberately does not add. Provider 429s are handled anyway (§5).

**Open issue: public demo fairness.** If "Explore the demo" signs every visitor into one shared
VIEWER user, all visitors share one 20-per-minute bucket and one conversation list, and one busy
visitor can spend the instance's daily LLM budget for everyone. Options for the architect (ADR-0011):
a per-visitor ephemeral VIEWER identity created at "Explore the demo", or rate limiting keyed by
session for the demo viewer. Until then the deterministic fallback keeps the demo usable when the
budget is spent.

**Public demo and VIEWER permissions.** VIEWER has `copilot.use` and no write permissions. Copilot
use by a VIEWER writes only that user's own `ai_*` rows, never shared business data.

## 7. Known limitations

| Limitation | Consequence | How the product states it |
|---|---|---|
| **Estimates** | Sales velocity and days of cover are a 28-day moving average (BR-150..152). They ignore seasonality, promotions, and stock-outs that suppressed sales | "Estimate" badge and `basis` text. The validator keeps them out of `facts` and `metrics` |
| **Data freshness = last import** | The product knows only what was imported. Orders, stock, and refunds that changed in the source system after the last import are invisible | Freshness line under every answer; a `limitations` entry with the last import time |
| **Exceptions lag live queries** | Exceptions reflect the last evaluation run (at most `evaluation_interval_minutes`, default 15, plus import-triggered and manual runs). Live tools such as `get_overdue_orders` can show newer conditions | The copilot states the difference when it sees it (`PROMPT_DESIGN.md §3`, rule 6) |
| **No forecasting model** | The copilot cannot predict demand, sales, or stock-out dates beyond the labelled estimates | Forecast questions get a refusal with an explanation |
| **Priority is a heuristic** | Weights are defaults not validated with real operators (`PRIORITY_MODEL.md`) | Priority caveat in `limitations` whenever a score is cited |
| **Exposure is not loss** | Gross order-line value at risk ignores margin and likelihood (BR-404) | "Value at risk" wording; validator rejects "loss" |
| **LLM variability** | The same question can produce differently worded or differently emphasised answers, and quality can change when the provider updates a model behind the same name. Free-tier models may also be smaller or more rate-limited than paid ones | Provenance label with model id; evaluation runs repeated per model (`EVALUATION_STRATEGY.md`); grounding validation applies to every answer |
| **Model availability** | Providers retire free-tier models and change quotas | `LLM_MODEL` is configuration, not code. Retirement surfaces as provider errors and the deterministic fallback |
| **Deterministic router coverage** | The rule-based assistant recognises the catalogue intents in English phrasings only. Other questions get the help answer | Help answer lists the supported questions |
| **Residual prompt-injection risk** | Text inside imported data may still change the wording or emphasis of an LLM answer (`PROMPT_DESIGN.md §5`) | References and labels let a person check every claim; no tool can act on injected text |
| **Synchronous turns** | A slow LLM request holds one API worker thread for up to the turn deadline | Short timeouts (20 s per request, 45 s per turn) and the per-user rate limit |
| **No automatic retention purge** | Conversations of non-demo stores are kept until the user deletes them (ADR-0009 allows no extra background jobs) | Documented here; a retention job is roadmap |
| **No evaluation results yet** | No quality, latency, or quota-use figure exists for any provider | `EVALUATION_STRATEGY.md §0` |
