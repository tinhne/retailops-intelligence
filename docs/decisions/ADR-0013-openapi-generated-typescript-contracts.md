# ADR-0013: OpenAPI-generated TypeScript contracts

| Field | Value |
|---|---|
| Decision ID | ADR-0013 |
| Title | OpenAPI-generated TypeScript contracts |
| Date | 2026-10-31 |
| Status | Accepted |

## Context

The API is Python (Pydantic v2 schemas) and the web app is TypeScript. Hand-maintained duplicate
types drift silently: a renamed field compiles in the frontend and fails at runtime. AGENTS.md §4
forbids hand-written duplicate response types, and §10 requires contracts to be regenerated when an
endpoint changes.

## Alternatives considered

### A. Hand-written TypeScript types

- **Pros:** full control over naming.
- **Cons:** drift is guaranteed over time; every API change is two edits that nothing checks.

### B. Schema-first: write the OpenAPI document by hand, generate server and client from it

- **Pros:** the contract is designed before code.
- **Cons:** duplicates the Pydantic models or requires Python code generation; slower iteration for a
  single developer who owns both sides.

### C. A typed RPC or query layer (GraphQL, or an end-to-end TypeScript RPC library)

- **Pros:** strong typing across the boundary.
- **Cons:** TypeScript RPC libraries need a TypeScript backend; GraphQL adds a server layer, tooling
  and caching semantics that a REST API with a small client does not need. Both are outside the stack.

### D. Generate runtime validators (for example Zod schemas) from OpenAPI

- **Pros:** responses validated at runtime.
- **Cons:** another generator and bundle weight; the API is first-party and its output is already
  validated by Pydantic. Zod remains in use for form input.

## Decision

- The Pydantic schemas and FastAPI route declarations are the single source of truth.
- A script exports the OpenAPI document without running a server, and `openapi-typescript` generates
  types into `packages/contracts`. Both the document and the generated types are committed.
- CI regenerates them and fails on any diff.
- Stable `operationId`s (`{module}_{action}`) and one tag per module keep generated names stable.
- The web app uses the generated `paths` and `components` types through a small typed fetch wrapper in
  `apps/web/lib/api`.

## Consequences

### Positive

- A breaking API change is a TypeScript compile error in the same pull request.
- No duplicate type definitions to maintain.
- The OpenAPI document doubles as reviewed API documentation.

### Negative

- Types only: responses are not validated at runtime in the browser.
- The quality of generated types depends on how schemas are written (explicit response models,
  string enums, `Decimal` serialized as string, explicit nullability), so those conventions must be
  followed (API_CONVENTIONS §13).
- Regeneration is an extra step in every endpoint change.
- Ownership needs clarifying: AGENTS.md §9 assigns `packages/contracts` to the Architect, while §10
  expects whoever changes an endpoint to regenerate it. Proposed: generated files are never edited by
  hand and are regenerated by the backend change that alters them; the Architect owns the generation
  configuration.
